# Agent Note: 当前批次、请求作用域与已完成响应分别决定提交归属

Status: implemented

## Problem

三个接缝把不同事实当成同一件事：搜索新增长度被当作本批返回总数；工具详情在解释项目路径前返回同名全局项；UI 旧响应可以覆盖新的选择。首轮请求令牌修复又把“最新发出”当作“最新可用”，持续慢于 3s 的 RPC 会使轮询一直无法展示结果。进一步回归证明：旧回调若在选择改变、cleanup 之前启动，不能在 load 入口重新认领当前 epoch。

## Decision

沿现有所有者只纠正事实，不修改排序、默认策略或轮询频率：runtime 给 discovery 的本批保护量使用已按完整工具名去重的返回总数；tools(payload) 提供 wsPath 时先使用共享路径验证并只查该项目，归属见 [项目工具定义所有权](2026-11-23-project-tool-definition-ownership.md)。ContextFace 的来源由选择、RPC 和可观察的宿主连接代次组成，布局提交与卸载即切换令牌；详情与该来源绑定，结果按已完成序号推进，loading 只由最近发出的有效请求收尾。

可机械判定的门槛：
1. 旧旧新混合、返回总数超过 cap 的 select，所有刚返回项都通过守卫，native 执行器可以实际派发；PTC 保持手册/绑定。
2. 全局同名非空或空，项目 A/B 返回各自真实已注册集合；非法路径拒绝，未传路径保留既有全局/无全局时项目兼容查询。
3. 新结果完成后旧 success/error/finally 不写回；选择已变而新 effect 未执行的窗口也不提交；卸载后写入为零；旧 poll/retry 在选择改变后不能重新发 RPC，旧 cleanup 不能作废新来源。
4. 同目标持续重叠慢轮询能展示依次完成的新数据，且在更晚请求尚在途时不错误停止 loading。

## Alternatives considered

1. 新增一个 discovery 批次提交 API。
   - 最强理由：一次拥有 discover/claim/evict/snapshot 可以结构性避免提交顺序错位。
   - 为何被否：当前只有一个生产提交调用方，现有状态层已经拥有预算规则；本缺陷是调用方传错数量，新 API 会扩散无必要的兼容/测试改动。
2. 对 select 硬截到 maxDiscovered 或仅返回新项。
   - 最强理由：当前呈现规模可严格固定，状态也更简单。
   - 为何被否：破坏已支持的合法显式大批次及旧项重复加载承诺，把调用正确性换成表面预算。
3. 保留全局优先、在前端规避同名服务器。
   - 最强理由：后端改动最少，既有无路径调用完全不动。
   - 为何被否：同名跨作用域本来合法，RPC 已携带 wsPath；绕开前端掩盖共享验证与数据归属错误。
4. UI 全部使用 latest-issued-wins 或阻止后续轮询。
   - 最强理由：单令牌容易判定，旧请求完全不能落地。
   - 为何被否：17 条回归中新增两条证明首次/持续慢 RPC 饥饿；阻止轮询又改变本批承诺不动的 3s 请求策略。

## Consequences

- 收益：返回即能调、按请求作用域返回工具、UI 提交单调且不因慢轮询饿死；没有新依赖或另一套调用通道。
- 代价：显式大批次仍可能暂时超呈现 cap；UI 在后续轮询尚未完成时显示最新已完成数据并保持 loading，内部必须分别维护来源、已发出序号和已提交序号；提供空/非法 wsPath 不再被同名全局项掩盖。
- 验证边界：native 走实际执行器，PTC 的持久测试覆盖守卫/手册/绑定；GUI 与完整宿主验证由本批独立实例完成，不等同所有模型线上成功率。
