# 发布等待同一提交的 CI 宿主矩阵

Status: implemented

## Problem

主分支 CI 跑三代宿主组合，标签发布却只重跑开发基线。即使另一次 CI 有失败，标签也能触发一个不依赖它的发布任务。生成物一致性检查也不能识别只在事件回调里使用的未定义标识符。

## Decision

[发布流程](../../../.github/workflows/release.yml) 调用同一提交的 CI，发布任务依赖它成功；验证任务不持有发布权限。客户端的标识符闸门用开发期 TypeScript 编译器解析发布脚本，只断言缺失名称，不把现有 JS 一次性迁成 TypeScript。

## Alternatives considered

- 查主分支此前的 CI 状态能省算力，但标签不一定指向相同提交；直接复用流程让提交与验证自然对齐。
- 在发布 YAML 再抄一份宿主矩阵更直观，但会产生两个可各自漂移的门禁。共用流程只维护一份。
- 给容易漏的回调补源码正则成本低，但发现不了未来另一个位置的自由标识符。解析产物与测试点击回调各守不同层。

## Consequences

- 标签发布前，生成物和受支持宿主验证是机器强制执行的，不再依赖人工等待另一条工作流。事件回调中未绑定的名称也会让 CI 失败。
- 给同一提交打标签会再次运行 CI，耗时高于只跑开发基线；新增一个固定版本、无传递依赖的开发编译器，不进入运行时依赖。
