# 项目配置快照决定提交与连接所有权

Status: implemented

## Problem

项目写入原来从一份配置规划变更、从另一份配置保留原文，新外部改动可能被旧计划覆盖。运行态把「读到了配置」「会话属于哪个项目」和「某次建连还有资格发布」混成同一事实；第一次保存找不到旧会话，已删除条目还可能由旧的待建任务重新发布。

## Decision

项目写入以同一份原文、解析结果和内容版本为输入，在宿主文件锁内校验该版本再原子替换。写后与新会话共用一个连接对齐器；会话归属不依赖文件存在。待建任务只有在自己的连接格仍被占用、配置版本仍有效时才可创建作用域；已建立连接被替换时，由原会话 effect 撤掉投射和引用。

## Alternatives considered

- 在提交时重读并混合新旧字段：可以少报冲突，但不能可靠知道旧计划会覆盖哪些编辑器新改动，继续冒静默丢数据的风险。
- 把写入、建连和销毁放进同一把大锁：顺序更容易证明，但一个慢连接会阻塞同项目后续保存，而且不能靠这把锁约束普通外部编辑器。
- 专门给移除待建连接加补偿：改动较少，但尚未有配置的会话和手改后旧连接仍不受同一规则管理，后续入口仍需自行补边界。

## Consequences

- 普通的并发修改可明确报冲突；首次保存、手改与面板写入共享归属规则，旧建连不能在新版对齐后发布。未变的已就绪连接仍复用。
- 提交多一次内容版本检查；遇到竞争时需要刷新重试。未参与文件锁的编辑器仍可在最后检查与 rename 之间保存。配置版本更替可能让尚未创建作用域的加载重试，但不会让旧任务先发布；连接释放和就绪等待不占文件写锁。
